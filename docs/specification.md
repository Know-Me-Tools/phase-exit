# Phase Exit first-pass requirements

Authority: operator-approved “Phase Exit: bounded, evidence-backed KBD completion”
plan,2026-10-16. This document expands the compact implementation-plan record;
it does not introduce new scope.

## S1 — Reproducible authority

The public Know-Me-Tools/phase-exit repository is Apache-2.0. The reusable Rust
engine and CLI use strict versioned JSON. Contracts identify project, phase,
revision, parent and adoption; assessment, analysis, specification and plan source
hashes; stable criterion IDs, references, expected outcomes, dependencies and
stages; mandatory predicates and exact approved acceptance actions; exclusions,
external prerequisites, complete implementation boundary and bounded attempts;
JEV model/rubric/thresholds and mandatory hook configuration identity.

Reject duplicate identifiers, missing references, cycles, empty acceptance and
unresolved contradictory requirements. Derive counts from inventory. Preserve
draft, reviewed and adopted versions; only explicit adoption changes authority.
Provide import/inspect/freeze/compare/propose/adopt, evidence import, evaluation,
exact action authorization, append-only learning, status and explain operations.
JSON stdout, diagnostic stderr and documented process exit codes are mandatory.

## S2 — Exhaustive outcomes and evidence

Every decision carries evaluated_stage, stage_complete, phase_complete, unmet IDs,
evidence references and the exact next_authorized_action or null. COMPLETE means
only the evaluated stage passes; phase_complete separately identifies full scope.
CONTINUE returns an already authorized action. WAIT means a matching operation
is actually running. BLOCKED stops on an unavailable external prerequisite.
REVIEW_REQUIRED stops on ambiguity, unknown impact or exhausted attempts. INVALID
stops on malformed, tampered or inconsistent identity. No new action is invented.

Bind receipts to original runner, exact command and terminal result, source and
fixture identities, platform, configuration and artifact digest. Retain original
bytes/hashes and failed receipts. Explicit valid dependencies are required for
carrying evidence forward; unknown impact requires review. One repaired group
cannot establish full-phase acceptance. Missing/stale proof permits only an
approved collection gate after complete implementation, not a presumed product bug.
The engine never runs commands embedded in criteria or imports executable evidence.

## S3 — Pinned semantic judgment

Use documented System One API from Rust and exact jev-1.14.0 **preview**. Read
JEV_API_KEY only from environment. The installation's Node bootstrap may read the
designated literal assignment without executing the profile or persisting its key.
Send minimized redacted packets with evidence references. Check exact response
model, keys, types, finite probabilities and bounds. Reject oversized input with
no silent truncation or automatic long-context enablement.

Fingerprint the full evaluation input/policy and cache terminal outcomes. Never
resample semantic uncertainty for a pass. Permit at most two transient retries.
Separate supported, contradicted and uncertain outcomes; initially accept only
support>=.95 and contradiction<=.05. Exercise the frozen known examples before
adopting thresholds. Changes require revision, not tuning to the UAR result.
A contradiction authorizes repair only when cited evidence and existing scope do.

## S4 — Learning and hooks

Append discoveries with evidence, affected IDs, classification and disposition:
clarification, observed in-scope defect, proposed new scope, external dependency,
deferred improvement. Amendment proposals expose readable changes and evidence
invalidation. Preserve superseded requirements and rationale. Semantics, required
evidence, model, thresholds and mandatory hooks require adoption.

Node ESM hooks support collection, evidence import, evaluation, judgment, final
decision and amendment events. Configuration specifies identity, order, input and
output schema, timeout, environment allowlist and blocking policy, snapshotted
for each evaluation. Hooks can propose evidence/amendments, veto or notify; they
cannot waive predicates, self-authorize or silently create mandatory scope.
Required failure prevents certification; optional notification failure is recorded.
Event identities and fingerprints prevent recursive dispatch. No JEV credential
is passed to hook children. Installed code is trusted, never advertised as sandboxed.

## S5 — Portable skills and native packages

Canonical Agent Skills: phase-contract and phase-exit, standard frontmatter,
progressive references, schemas and examples. Generate copies. All scripts,
installers, hooks and adapters use Node24.22.0/TypeScript7.0.2 and distribute JS.
Use filesystem APIs and executable/argument arrays, no Bash/Python/Unix facilities
or symlink installers. Host-required command strings use fixed Node launchers.

Native targets: Claude2.1.301 plugin/repository marketplace; Codex0.163.0
plugin/repository marketplace/trusted lifecycle hooks; OpenCode2.0.31 V2/local
install; Kimi2.2.0 current manifest/custom marketplace; DeepSeek0.2.0-rc.2 Cordis
skills/tools/guards. Stop success, running yield, blocker/invalid/uncertain stop,
and bounded authorized continuation must remain distinct. Record packaged,
fixture-tested and actual host exercise separately. No public-directory approval
claim for Codex lifecycle-hook packages.

Track license, README, contribution/security guidance, lockfiles, schemas,
research, bounded phase records, compiled distributables and .prometheus history.
Ignore caches, credentials, private evidence and archives. Versioned artifacts or
repository marketplace delivery, no automatic updates or shell installers.
Write MCP server (stdio/Axum Streamable HTTP/current stable rmcp) and dependent
MCP app issue drafts. These are not first-pass implementation gates.

## S6 — Complete first, then verify

Use exclusive lead/Rust/TypeScript/UAR ownership and an isolated artifact reviewer.
Finish all production behavior, fixtures, skills, docs, packages and issue drafts
before the implementation-complete inventory. Then one serialized bounded real
CLI/filesystem/JEV/hook/UAR program covers the cases in acceptance-plan.md.
Controlled errors supplement actual service and production-path exercise.
No Windows host/setup/matrix, legacy-host qualification, broad benchmark,
unrelated UAR test or repeated passing gate belongs to this delivery.

## S7 — The UAR example

Preserve the current frozen candidate and running acceptance; no duplicate build
or source edit until terminal. Read original records without executing Python.
Reconcile19 listed items versus17 count and obsolete seven groups versus approved
six. Freeze six image groups, four exact real-source supplements, review limits,
publication provenance, both architectures and release/issue receipts.

After the active program ends, collect all observed failures, complete the repair
cohort, renew full inventory and rerun only affected approved gates. Every local
gate must pass before source/tag/image publication. Full acceptance on both
published child digests precedes release and issue receipts. Missing genuine
qualified supervision remains a mandatory external blocker. Never fake it, revive
cancelled qualification, mutate know-me production or silently move a tag.
Retain a sanitized case study with actual discoveries, amendments and outcome.

The uncomfortable limit: this system decides against adopted evidence; it cannot
prove all possible defects absent or prevent privileged bypass. A truthful
BLOCKED UAR result demonstrates stopping, not a successful v1.1.1 release.
